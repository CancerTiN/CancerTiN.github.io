这次思考起于变异解读。围绕一个基因变异，查找资料、核对证据、追问已有结果，可能需要多轮调查。我关心的是：这些步骤应该提前写进程序，还是可以让 AI 根据调查结果，自己决定接下来查什么、调用什么工具？

最初，我问的问题很具体：现在已经可以让 Coding Agent 写代码，开发这样的应用，应该用现成框架，还是让它自己实现？讨论下去，我开始关注执行过程本身：**下一步做什么，由谁决定？**

沿着这个问题，我重新理解了自己目前所处的位置，也开始觉得，下一步可以直接面向变异解读 Agent 设计。

## 四种形态，执行决策权逐步变化

我把这几种系统组织方式整理成四类：

1. **传统生信工作流**，Traditional bioinformatics workflow。
2. **LLM 增强工作流**，LLM-powered workflow。
3. **嵌入 Agent 的工作流**，Agentic workflow。
4. **变异解读 Agent**，Variant interpretation agent。

这套划分服务于本文的讨论。其中，第三类具体指在既定流程中引入局部自主执行。理解这些形态，最有用的线索是看谁安排步骤、谁根据结果调整行动。

传统生信工作流由程序组织执行路径。调用哪个分析工具、查询哪些数据、怎样处理输出，都由预先写好的步骤和分支安排。

LLM 增强工作流在这些步骤里引入模型，让它提取信息、理解文本、辅助判断或生成解释。模型承担了更复杂的任务，整体流程仍由程序安排。我目前的实践主要处在这一类。

嵌入 Agent 的工作流把某些环节交给 Agent。例如，主流程进入资料调查阶段后，由 Agent 根据已找到的信息继续检索、核查疑问，再把结果交回主流程。它在局部决定行动，整个任务仍有预设的组织方式。

变异解读 Agent 则围绕解读目标安排调查：检查已有信息，选择工具，根据返回结果继续追问，并检查任务是否完成。具体计算可以由程序执行，解读规则、复核要求和权限边界继续作为约束。

Anthropic 在[《Building effective agents》](https://www.anthropic.com/research/building-effective-agents)中，也把预设代码路径与模型动态安排执行过程作为 workflow 和 agent 的主要区别。本文的四类是在这个区别上，为自己的问题作出的整理。

ReAct 可以帮助理解这种反馈循环：行动取得外部信息，再据此调整接下来的行动。[ReAct 论文](https://arxiv.org/abs/2210.03629v3)讨论了推理与行动交替的方式。在这里，我更关心系统能否根据反馈推进任务，具体实现可以随需求选择。

## 我改变了怎样的理解

起初，我关注的是实现方式：选什么框架，怎样连接模型和工具，哪些部分让 Coding Agent 来写。这些问题都与开发有关，但还没有回答应用本身怎样组织任务。

看清四种形态之后，我开始把两个问题分开：**谁来实现软件，以及软件运行时由谁安排执行。**

Coding Agent 可以帮我实现一套固定工作流；同样，它也可以帮我实现一个根据反馈自主调查的 Agent。开发工具相同，最终交付的系统可以有不同的组织方式。

我现在更关注的问题变成了：

| 原先主要关注 | 现在进一步关注 |
| --- | --- |
| 在哪个步骤调用模型 | 哪些执行决定适合交给 Agent |
| 怎样连接模型与工具 | 工具需要提供什么信息，才能支持下一步行动 |
| 某次输出是否正确 | 整个调查是否完成，结果依据是否清楚 |
| 用框架还是自己实现 | 哪种实现能支持状态、反馈、恢复和验证 |

框架问题仍然存在，只是有了更具体的判断依据。先说清系统需要怎样运行，再比较实现方式，选择就更容易落到实际需求上。

## 下一步，我倾向于直接面向解读 Agent

四种形态可以帮助理解变化。对我接下来的方向，更有吸引力的路径是：**从当前的 LLM 增强工作流，直接以变异解读 Agent 为架构目标。**

设计时，先考虑 Agent 要完成什么任务、能使用哪些能力、怎样保留调查状态，以及用什么标准检查结果。已有的分析、检索和计算能力，可以作为它调用的工具；确定性的检查继续负责各自明确的规则。

这样安排之后，某次工具调用的结果就能够影响接下来的行动：信息充分时结束调查，出现疑问时补充查询，遇到需要人工判断的问题时请求介入。系统围绕任务状态推进，执行路径可以随反馈调整。

实施时仍可以从范围明确的任务开始，逐步增加工具和可执行的动作。每增加一项能力，都检查它怎样影响任务完成质量。局部 Agent 可以出现在这个过程中，整体设计则从一开始就服务于解读任务。

我看重的是尽早确定这个组织方向。工具接口、执行记录、状态和评测都围绕它积累，之后扩展能力时，就有一套共同的基础。

## 为什么我看好这个长期方向

我的长期判断是，应用会越来越多地把执行决策交给 Agent。模型处理目标、使用工具和根据反馈纠错的能力越强，系统就越有机会覆盖开发者事先没有完整写出路径的任务。

对于需要调查的问题，情况越多，提前维护所有分支的成本就越高。如果一个系统能够组合已有工具，根据新信息继续行动，它就有机会处理更多变化。长期停留在固定调用链上的应用，会持续面临这种适应能力带来的竞争压力。

我预期，直接面向解读 Agent 设计有三方面的优势。

**工具能力可以反复使用**：新增一个检索或分析工具后，Agent 有机会在不同任务中调用它，并结合已有结果选择用法。开发工作可以更多地用于建设可靠的能力和清楚的接口。

**模型进步更容易转成任务能力**：当模型更擅长规划和使用工具时，已有能力之间可能形成新的组合。清楚的输入输出、完整的反馈和可恢复的状态，会为这种组合提供条件。

**验证可以覆盖整个任务**：除了检查某次回答，还要看调查是否遗漏关键问题、工具失败后能否恢复、结果依据是否可追溯，以及完成任务需要多少时间和人工介入。这些评测能帮助判断，提高自主性是否带来了实际收益。

这些是我选择这个方向的理由。具体收益需要在任务中观察和比较，模型能力、工具质量和验证方式都会影响结果。

## 我的开发方式已经先走了一步

讨论到未来工程师可能主要负责目标、约束和验收时，我的反应是：「现在已经是了，至少我是。」

这个站就是一个可以公开说的例子。在[建站记录](/posts/building-this-site/)里，我写过自己的工作方式：提出需求和条件，让 Agent 起草、实现、检查和修改，我审阅结果，决定什么时候发布。

开发过程中，Agent 可以根据检查结果继续修正；生成的网站则按既定代码运行。这让我更容易分清开发过程与产品运行，也让我看到自己关注点的变化：把任务描述清楚，提供合适的环境，让结果有依据、有检查、有明确的完成标准。

对变异解读应用，我目前仍处在 LLM 增强工作流阶段。接下来值得探索的是，把这种围绕目标推进、根据反馈调整、对结果进行验证的组织方式，落实到应用本身。我的关注也随之从怎样安排每一次模型调用，扩展到了怎样让 Agent 完成一项调查任务。
